# Conversational Console behavior and oracle matrix

The matrix precedes implementation. **M** is spec-derived from a maintainer
decision in [the request recorded by TASK-012](./spec.md#maintainer-decisions).
**P** is an independent proposed oracle derived from this spec before
implementation and pending maintainer review. **C** is implementation-aware
baseline compatibility, identified by its existing criterion or contract.
**X** is an external adapter contract, with independent live qualification
required. The new oracles must be reviewed before tests are implemented.
[Delivery evidence](./evidence.md) records local verification by feature, including the monitor → second chat → return journey, review races, native restore and PR 418 across three SCM fixtures. The operation inventory records the design baseline. Consult the [operator guide](../../../docs/features/chat/README.md) for available actions and handoffs. External and device qualifications remain open.

## Behavior and oracle matrix

U = unit (Go/TypeScript or UI component). I = integration (real collaborating
components). E = browser end-to-end. For I with storage, use an on-disk store,
close/reopen it when specified and verify records from the API/durable state
rather than component mocks. Providers can be deterministic fixtures for core
tests. A fabricated client response or a memory store alone cannot qualify
restart, receipts, concurrent CAS, roles, HTTP or OAuth state. Inspect stored
effects and negative cases, including zero effects where the contract forbids
a write. Live transport/data tests support only the editions actually exercised.

API role (higher roles inherit lower permissions). Resource scope and service

executable Chat action. **External** means a selected account/edition and scope
requires independent qualification. Operations outside P1–P4 use the retained manual workflows. This is a
delivery boundary: a later typed action requires a reviewed target, eligibility,
confirmation and recovery contract. Planned Weft capabilities remain
distinct from existing manual actions and unsupported editions.

### Declarative configuration baseline

`server/internal/installation/document.go` accepts `weft.io/v1` kinds
`InferencePlugin`, `ModelProvider`, `PriceCatalog`, `CostPolicy`, `Budget`,
`NetworkPolicy`, `MCPConnection`, `SCMConnection`, `IssueConnection`,
`IssueWorkflowMapping`, `JiraCloudProfile`, `JiraCloudWorkflowMapping`,
`Project`, `Graph`, `PullRequestReviewRoute` and `IssueTrigger`.
The five kinds added since OPS-003's original eleven-kind list already appear
in the current [operator guide](../../../docs/declarative-configuration.md#object-kinds).
The catalog agent and runtime task/control contracts remain separate.

The handlers in `server/internal/api/config.go` accept files, baseline
revisions, explicit per-object force and optional recordConsent. Plan
validates without writing. Apply requires confirmation and expected revisions
from the reviewed plan. It revalidates the entire reviewed snapshot before the
first write and each object before mutation. Baseline conflict, stale review
and a stop-on-error batch can appear in an HTTP 200 response. Show each
applied/unchanged/failed/not-applied result. A saved object with an unreadable
revision is uncertain evidence and needs an export/re-read before retry.
Plan shows repository import effects, and apply reuses existing
connection discovery/tests when applicable. It does not start builds.
Console/CLI changes can invalidate the reviewed operation. Scoped force
never bypasses authorization or rechecking a stale reviewed plan. Chat must
reuse compatible revision, secret reference and consent rules, including
configured server-side refs and omission/preservation of stored credentials.
